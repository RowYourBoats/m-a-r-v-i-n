Data Model

Each bullet carries structured metadata alongside its text. Two fields control how bullets are organized and selected.

  1. size -- "large", "medium", or "small". Large = full narrative paragraphs (company/project context). Medium = detailed bullet. Small = concise bullet. Bullets without a size are treated as small.
  2. project -- the project name within a company (e.g. "Picnic", "5G Flagship Store"). Groups size variants together so the pipeline can swap between densities.
  3. Other fields: company, role, date, category, tags, pinned
  4. Categories: experience, teaching, education, exhibition, award, skill, writing
Resume Generation

The core pipeline. Extracts requirements from a job description, scores every bullet against them, then generates a tailored resume. The pipeline is size-aware -- it searches concise bullets for precision, then expands to richer variants for the LLM.

JD file -> Extract requirements -> Search (small only) -> Score bullets -> Apply match memory -> Select top 25 -> Expand siblings -> Organize by company -> LLM generates resume
  1. Split the JD into ~15 actionable requirement phrases, filtering boilerplate (salary, EEO, benefits)
  2. For each requirement, semantic search returns top 10 bullets. Large bullets are excluded from search -- they embed poorly due to length. Also runs global JD match and tag-concept search
  3. Score each bullet: best single-requirement match x3.0 (depth wins) plus breadth bonus for covering multiple requirements
  4. Apply match memory -- boost bullets kept in similar past JDs (+0.5), penalize removed ones (-0.3)
  5. Select: pinned bullets first, then best-per-requirement nominees, then fill by score up to 25
  6. Expand siblings: for each selected small bullet, look up its medium sibling (same company + project) and swap it in for richer LLM input. Collect all large bullets for selected companies as narrative context
  7. Group by company/role, sorted by relevance (strongest company first). Cap at 6 per company. --chronological instead orders roles by end date, most recent first ("Present" on top) -- relevance still decides which roles appear and breaks date ties
  8. Large narratives are injected as company context in the prompt, replacing LLM-generated context docs. File-based context docs serve as fallback for companies without large bullets
  9. Save both rendered resume and a raw copy (for later review)

Use --dry to preview the mapping and graveyard without generating. Use --simple for single-shot mode.

Output & exports
  1. Every run writes to a per-job folder named <company>_<role>_<date>, with files stemmed <name>_<role> so they read as portfolio artifacts on their own
  2. Always written: the rendered resume .md and a raw copy (the pre-render baseline resume review diffs against)
  3. --docx adds a Word .docx styled from the template, a condensed 2-page variant (_2pg.md + _2pg.docx), and -- unless --no-pdf -- a matching .pdf beside each .docx
  4. PDFs render through the installed Word app, so they match the .docx line-for-line and embed the fonts -- the fix for mobile, where an opened .docx falls back to a system font
  5. The export step is partial-failure tolerant: if .docx or PDF fails, the .md is still on disk and the run is marked partial rather than errored

PDF fidelity needs Microsoft Word installed and PP Neue Montreal installed for all users (machine-wide). Word automation can't see per-user fonts and silently substitutes Arial into the PDF.

Batch Generation

Run the resume pipeline across many job descriptions in one warm process. The store and Ollama client load once, so the model cold-start cost is paid a single time instead of per JD.

JD files / directory -> Expand + filter -> Per JD: full pipeline -> .md + .docx + PDF -> Summary table + JSON
  1. resume batch <jds...> takes any mix of JD files and directories. Directories expand to their *.md children, skipping _template*
  2. Each JD runs the same pipeline as resume query, writing .docx + a matching PDF by default. The warm process amortizes model load across the whole batch
  3. Continues past per-JD errors by default and reports them at the end. --stop-on-error halts on the first failure
  4. --skip-existing skips JDs already generated within the last 7 days (--skip-within-days N to tune, 0 = same day only). Only folders that actually contain a resume count, so an empty/half-built folder never causes a skip. The default re-runs and overwrites (folder layout is idempotent)
  5. Prints a per-JD summary line and writes a batch_*.json sidecar to the output dir recording status, company/role, and which artifacts succeeded

Flags: --no-docx (markdown only), --no-pdf (skip the PDFs), --top-n, --model. Same Word + machine-wide font requirement as single-JD export.

Cover Letter

Two modes: build a kit for manual assembly, or have the LLM draft one using your voice samples.

Kit mode (default)
  1. Extract requirements from JD
  2. Match bullets and narratives per requirement
  3. Output a structured markdown kit: narratives up top, then per-requirement sections with matched bullets and narratives
Generate mode (--generate)
  1. Same matching as kit mode
  2. Collect top 10 experience bullets, matched narratives, and all voice-sample narratives
  3. LLM drafts 3-4 paragraphs. Every claim must trace to a bullet or narrative. Voice samples set tone but are not quoted
Gardening

Bulk editing and quality control for your bullet library. Two garden file formats are supported.

Narrative format (default)
  1. Garden files use # Company — Role headers, ## Project subheaders, and **Large** / **Medium** / **Small** size markers
  2. Large sections contain full narrative paragraphs. Medium and Small are dash-prefixed bullet lists
  3. Special sections at the bottom: Teaching, Exhibitions, Education, Awards, Skills, Writing
  4. resume garden-import auto-detects narrative format by the presence of size markers
Legacy format
  1. Flat structure: ## Experience > ### Company | Role > - bullet
  2. No size or project metadata. Auto-detected when no size markers are found
Export
  1. resume garden exports in narrative format if any bullets have size metadata, otherwise legacy
  2. resume garden --format csv exports as CSV regardless
Web dashboard
  1. resume garden --serve launches a dashboard on localhost:5000
  2. Unified table with five columns (where, when, what, how, tags) across all sections: Roles, Projects, Exhibitions, Education, Awards, Skills
  3. Detail slider on Projects toggles between large/medium/small view -- fallback shows the closest available size
  4. Pinned bullets show at full opacity, unpinned are dimmed. Click a row to toggle
  5. Sortable column headers with chronological date sorting
  6. resume garden --chat starts an interactive curator chat
Deduplication
  1. For each bullet, semantic search for near-duplicates above a similarity threshold (default 0.85)
  2. For each pair: keep one, merge with LLM, or skip
  3. --auto keeps the longer bullet automatically
Retagging
  1. LLM extracts tiered tags per bullet: PRIMARY (specific tools, projects, metrics) and ~SECONDARY (broad skills)
  2. Uses existing tag vocabulary to prevent drift
  3. Default merges with existing tags. --replace overwrites
Context Documents

Per-company narratives that feed into resume generation. Large bullets in the narrative garden format now serve as the primary source of context, with LLM-generated context docs as a fallback.

From garden (primary)
  1. Large bullets written in the garden file are hand-authored narratives per project
  2. During resume generation, expand_with_siblings() collects large bullets for selected companies and injects them as context in the LLM prompt
  3. Higher quality than LLM-generated context because they contain specific details, names, and first-person perspective
From LLM (fallback)
  1. resume context generate groups bullets by company (minimum 3) and asks the LLM to synthesize a narrative
  2. Used as fallback for companies that lack large bullets in the garden
  3. resume context list shows all context docs. resume context derive <company> generates new bullets from a context doc
Team Bios

Hand-written per-company prose about the team you worked on. Indexed separately and surfaced during resume generation alongside context docs.

  1. Add .md files to the team bios directory with company/role frontmatter
  2. resume team-bio index indexes all bios into a dedicated ChromaDB collection
  3. resume team-bio search "query" finds relevant bios by semantic search
  4. During resume generation, matched team bios are included as additional context for the LLM
Narratives

Prose voice samples and experience narratives used in cover letter generation.

  1. Add .md files with type and tags frontmatter to the narratives directory
  2. resume narratives lists all loaded narratives with type and tags
  3. resume narrative-add <file> copies a file into the narratives directory
  4. During cover letter generation, narratives are matched per-requirement and voice samples set the tone
Learning Loop

The system learns from your edits. No training -- just score adjustments and new bullet variants that compound over time.

Generate resume -> User edits -> resume review -> Diff + ingest -> Match record saved -> Future scores adjusted
  1. Generate a resume with resume query (saves both rendered and raw copy)
  2. Edit the resume -- remove weak bullets, reword others, add new ones
  3. Run resume review <edited> --jd <jd>
  4. The system diffs the original against your edits:
Kept -- bullet confirmed. Tracked in match record
Removed -- bullet rejected. Penalized -0.3 for similar future JDs
Reworded -- new variant ingested as a separate bullet (>= 75% word overlap detected)
Added -- new bullet ingested with metadata extracted from context
  1. Match record (YAML) stores kept/removed bullet IDs tied to this JD
  2. On next resume query, apply_match_memory() finds similar past JDs by word overlap and adjusts scores
  3. Over multiple review cycles, selection converges toward your preferences without any model retraining
Data Ingestion

Multiple ways to get bullets into the system.

  1. resume add "text" --company X -- single bullet with metadata (supports --size and --project)
  2. resume ingest -- bulk ingest all .md files from input/bullets/
  3. resume ingest-resume <file> --tag -- parse an existing resume into individual bullets with auto-tagging
  4. resume watch -- continuous file watcher that auto-ingests on create/modify/delete
  5. resume playground ingest -- sandbox ingest for experimentation, promoted to main store with playground promote
  6. resume migrate -- one-time migration from old directory layout (bullets/, data/) to input/ structure

All bullets are stored as markdown files with YAML frontmatter (including size and project fields) in input/bullets/ and indexed in ChromaDB with Ollama embeddings.

Playground

An isolated sandbox for experimenting with bulk PDF/MD ingestion before committing to the main store.

PDFs / MDs -> playground ingest -> Review (list / garden) -> playground promote --all -> Main store
  1. resume playground ingest [folder] parses PDFs and MDs into bullets in a separate ChromaDB collection
  2. resume playground list and playground garden let you review before committing
  3. resume playground promote --all copies playground bullets and files into the main store
  4. resume playground purge clears the sandbox without touching main data

Run resume deduplicate after promoting to clean up overlaps with existing bullets.

Snapshot Diff

Track changes to the store over time.

  1. A snapshot of bullet IDs and text hashes is saved after each ingest or garden-import
  2. resume diff compares the current store against the last snapshot
  3. Shows added, removed, and modified bullets with a summary count
