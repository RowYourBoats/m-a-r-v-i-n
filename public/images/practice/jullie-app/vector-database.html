Mental Model

Your career is stored as a pile of short text records, each one turned into a list of numbers (an embedding) that captures its meaning. A job description is turned into the same kind of numbers, plus a few other lenses. "Matching" is measuring which career records sit closest to the job description in that number-space -- then re-ranking with some non-vector signals on top. The career corpus never changes when you run a new job; only the question changes. Same subject, different viewer, different view.

One correction to the usual intuition: this is not purely a vector database. Vector similarity (semantic search) is one axis out of five. In the current weights, literal keyword hits are weighted higher than vector similarity. The vectors do the recall; the other axes do much of the ranking.
Two Halves

Everything is one of two motions. The write path turns a markdown file into embedded records (add, ingest, garden-import, web edits). The read path turns a job description into queries that rank those records (query, batch). The store in the middle is ChromaDB in data/ -- the only persistent index. The markdown files in input/bullets/ are the source of truth; Chroma is the derived, queryable copy.

input/bullets/*.md -- write --> ChromaDB (data/) <-- read -- job description
Write Path -- a bullet becomes a vector

How text on disk turns into something searchable. Each step is a function you can read in the source.

.md file -> parse to unit -> expand per size -> Ollama embeds text -> store record + metadata -> LLM enrich (tags + signals)
  1. File to unit. parse_bullet_unit() reads a file into a BulletUnit -- one editorial idea with shared metadata (company, role, date, project, tags, signals, stable id) and up to three size bodies (## Small / ## Medium / ## Large). The 6-char unit_id is assigned once and never regenerated, so edits and re-imports stay anchored.
  2. Unit to per-size records. to_bullets() expands the unit into one record per non-empty size body, keyed {unit_id}:{size}. They share all metadata but each gets its own embedding from its own body text -- so Small and Large renditions of the same project sit near each other but aren't identical.
  3. Text to embedding. The actual vector step. On upsert, ChromaDB sends the body text to Ollama (model qwen3-embedding by default, set in config.yaml) which returns an embedding -- a fixed-length list of numbers encoding meaning. Similar work lands near; unrelated work lands far. Nearness is cosine distance (hnsw:space: cosine).
  4. The stored record. Each Chroma record holds an id, the raw document text, the embedding, and a flat metadata dict of scalars. Metadata matters because the read path filters and scores on it without touching the vectors.

You never see the numbers -- they're an internal coordinate system. The only time a vector surfaces is as a similarity score (1 - distance) in search results.

Enrichment -- tags & signals

Raw text alone is a weak handle. Two LLM passes enrich each experience unit. The difference between them is intentional: tags describe, signals certify.

Tags (open vocabulary)
  1. Two tiers: PRIMARY (specific -- tools, projects, deliverables) and SECONDARY (broad capability, prefixed ~)
  2. Reuse-existing-vocabulary is enforced so the tag space stays coherent instead of sprawling
  3. Auto-runs on add and garden-import for untagged experience units; retag re-runs it deliberately
Signals (closed vocabulary)
  1. A fixed capability set in CAPABILITY_DEFINITIONS (e.g. brand-system-scale, design-systems, visual-craft, technical-narrative-translation)
  2. The prompt asks "what is this bullet credible evidence of?" -- not what it's about, but what it proves
  3. 0-4 tokens per bullet, "fail rather than reach." You extend the vocabulary by editing the dict, not by letting the LLM invent
Read Path -- a job description looks at the corpus

A JD is not turned into a single query. It is fractured into three lenses, each interrogating the corpus a different way.

JD text -> requirements + keyphrases + capability signatures -> score & rank bullets
  1. Requirements. The JD is split into sentences, boilerplate (comp, EEO, location) is dropped, and each line is weighted -- hard requirements 1.0, ambiguous 0.5, culture 0.3. Each is semantic-searched on its own, so every distinct ask gets its own shot at surfacing a bullet.
  2. Keyphrases. 12-20 weighted phrases that appear literally in the JD. A verbatim filter throws out anything the LLM hallucinated or paraphrased. Multi-word phrases decompose into single-word backoffs at reduced weight so partial hits still earn credit.
  3. Capability signatures. The JD abstracted into 5-10 underlying capabilities ("brand-system-at-scale"), each grounded in both the closed signal vocabulary and your existing tags. The deepest lens -- what the employer is actually hiring for beneath the wording.
The Five Scoring Axes

Every candidate bullet is scored as a weighted blend. Weights live in config.py and are tunable.

keyphrase -- literal JD keywords the bullet text contains (weight 2.0 -- highest)
semantic -- best vector similarity to any requirement (weight 1.5)
signature -- match against capability signatures, itself a blend of vector + signal + tag (weight 1.5)
tag -- fraction of JD tags the bullet also carries (weight 1.0)
breadth -- small bonus for covering multiple requirements (weight 1.0)
The headline: keyphrase (2.0) outweighs the semantic vector axis (1.5). The vector database does the recall -- it finds candidates worth considering at all -- but literal keyword overlap does more of the ranking. If a bullet you expected didn't surface, check whether it shares actual words with the JD before suspecting the embeddings.

After scoring, a few cleanups run: a company-affinity bump for the best-fit company, unit-level dedup (only the strongest size variant of a project survives), near-duplicate suppression, and phased selection (pins first, then each requirement's best bullet, then fill by score). Large bodies are excluded from selection throughout -- they're matching context, not resume content.

Viewer & Subject

What happens to the view of your career when the thing doing the looking changes position. This maps onto the architecture cleanly, and it tells you what the system can surface.

  • The subject is fixed. Your corpus -- embeddings, tags, signals -- is computed once at ingest and doesn't move when you run a job. A fixed constellation of points in meaning-space.
  • The viewer is the JD. A job description is a position in that same space plus a set of lenses. Running a query is placing the viewer somewhere and asking "what's nearby, and bright, from here?"
  • Move the viewer, the view changes. A design-systems JD and an experiential-events JD stand in different places. The Herman Miller brand-pillar bullet is bright from the first, dim from the second -- not because the bullet changed, but because the angle did. Nothing was rewritten; the projection rotated.
  • The lenses change the view independently of position. Two JDs near each other in vector space can still pull different bullets if their literal keyphrases or capability signatures differ -- those axes care about wording and certified capability, not geometric nearness.
  • Coverage gaps are viewer-relative. A capability signature with no bullet above the confidence threshold is a gap from that viewpoint -- something this employer wants that your corpus can't prove. Move the viewer and the gaps move.
  • Drift over time. Because the viewer is data, you can hold one JD still and watch how your answers to it change as you add bullets. The viewer holds, the subject grows, the view sharpens -- the longitudinal signal of a maturing corpus.
  • A self-portrait view. The viewer needn't be an external JD. Point it at your own stated ambition ("creative director, brand-led, AI-native studio") and the same machinery surfaces which bullets already argue for it and which signatures stay ungrounded. The subject becomes its own viewer.

The clean way to hold it: embeddings give you a space, lenses give you a question, the JD gives you a standpoint. Change any of the three and the view changes while the career underneath stays exactly what it is.

What It Can Surface Over Time

Beyond per-JD resumes, the same store already supports -- or is a short hop from -- these views.

  1. Capability coverage map -- which closed-vocab signals your corpus can prove vs. which are thin or empty. A direct read on what to go do, not just what to write
  2. Company x capability matrix -- the matrix view already crosses companies with tags; signals would make it crossings of proven capability by era
  3. Gap-to-target -- given a target role described once, the set of signatures it needs that your corpus doesn't yet ground
  4. Redundancy / over-indexing -- clusters of bullets sitting on top of each other in vector space mean you're saying one thing many ways; the dedup logic already detects this
  5. Vocabulary drift -- tags appearing on only one bullet (caught by the frequency gate) are noise the system already distrusts; surfacing them invites cleanup
The Ingestion Dashboard — shipped

The write-side console now lives in the garden UI (garden --serve → /ingest). It makes the ingest → enrich → store pipeline visible and stepwise instead of a one-shot CLI call, with you in the loop at each step.

paste / PDF -> split & size -> review tags + signals -> embed & commit -> coverage feedback
  1. Intake -- paste text / a resume, or upload a PDF (_extract_pdf_text + _parse_resume_lines). Output: drafts — JSON staging records in input/_drafts/, outside bullets_dir so the loader/watcher never embed them
  2. Split & size -- split breaks a body into one draft per sentence; the inline editor drafts Small/Medium/Large bodies. Still nothing embedded
  3. Review tags & signals -- per-draft propose tags / propose signals run the enrichers on demand; approve or edit before commit. The single biggest quality lever — everything downstream rides on tag/signal accuracy
  4. Embed & commit -- commit_draft is the only embed point: write the .md → upsert_unit → delete the draft, in that order, so a failed embed leaves nothing half-done
  5. Coverage feedback -- a live coverage strip shows per-signal counts; each commit flashes the before/after delta (design-systems 0→1), so you add bullets toward gaps, not blindly
Core invariant: a draft is never embedded until you commit. What it isn't: not a resume builder, not a writing tool — an ingestion and enrichment console that orchestrates existing functions (write_bullet_unit, upsert_unit, the enrichers) rather than replacing them. New code is one module (ingestion.py) plus two templates.
The Capability Timeline — shipped

/timeline answers "when did each capability first surface, and where does it recur?" — two renderings of one deferred aggregate (capability_timeline), toggled client-side.

  1. Milestones (default) -- each capability as a row ordered by the year it first appeared, with the originating role. A single-proof-point capability is flagged "thinly proven" — the hook for adding new roles as evidence
  2. Bands -- a capability × year grid marking every recurrence, first occurrence highlighted. Same data, denser view

Needs the signals field populated — that's what the dashboard's review step is for going forward. To backfill the existing corpus in one pass, run resume retag-signals (CLI); until then the timeline shows an empty-state hint. A new _start_date_key (LHS mirror of query._end_date_key) parses the start of each date range so "first surfaced" is real.

Source Map
  1. embeddings.py -- the Ollama embedding function (text to vector)
  2. store.py -- ChromaDB wrapper: upsert_unit, search, cosine space, metadata round-trip
  3. models.py -- Bullet / BulletUnit, to_bullets(), bullet_to_metadata, stable unit_id
  4. query.py -- the whole read path: requirement / keyphrase / signature extraction, CAPABILITY_DEFINITIONS, the five-axis blend in select_bullets
  5. config.py -- the scoring weights (score_alpha_semantic through score_epsilon_signature) and quality gates
  6. ingestion.py -- write-side console: Draft + I/O, commit_draft, signal_coverage / capability_timeline (with _start_date_key); routes in garden_web.py, views in templates/web/ingest.html + timeline.html
  7. docs/bullets.md -- the unit model and storage layout in more depth
